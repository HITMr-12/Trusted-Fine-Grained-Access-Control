## 当前结论边界

该分支实现了针对固定五列、固定 PLAIN/ZSTD 布局的掩码传输原型。其数据通路与当前数据集可以验证，但尚不能等同于完整、通用的可信细粒度访问控制系统。新端到端复测支持中高选择率的通路收益，但低选择率有明确代价；真实无效身份与断流检查暴露了授权和部分结果误提交问题，原报告“全场景可靠”的结论不成立。

## 静态审查与历史证据复核

1. **MASK 没有执行与 FGAC/NATIVE 等价的授权。** `bench-tpcds/mask_e2e_server.py` 接受调用方提供的 `thr/host/port`，没有 token 验证、可信策略查询、主体行策略、授权列校验或策略版本重验。`thr=NONE` 直接全放行；`mask_e2e_producer.py:146` 的 keep 只依据价格。正式比较仅使用 `bench_full` 全表授权主体，实际扫描的是业务谓词选择率，不能证明 alice/bob 的安全行策略与 MASK 一致。若将 R 服务定位为可信网关后的内部算子，必须补齐并测量该网关，才可宣称系统级公平对照。

2. **历史最终结论没有同轮资源对齐。** `aligned-0917/aggregate_s14.py` 将 MASK 三个文件共 9 rep 与 `records3.jsonl` 的 NATIVE/FGAC 各 3 rep 比较；最终 MASK16 与基线并非同一交错实验。报告 §15.2 以串行生产时间小于 E 消费时间推断并行度不影响总延迟，这忽略了首包、分批调度、关键路径和尾部排空，不能替代真实端到端消融。

3. **历史结果本身未发现摘要或中位数算错。** 独立忽略 `equal` 标志、逐条比较真实 `digest`：72 条 MASK、72 个唯一标签，8 案例每案 rep1–9 完整，与相应 NATIVE/FGAC 摘要一致。历史中高选择率中位数优于 FGAC 约 26.5%–34.1% 的算术可重算。它证明这些特定查询的输出摘要一致，不证明授权、可用性和普遍性能归因。

4. **接收完成协议不可靠。** `recv_server.py:44–65` 把文件边界 EOF 当作成功，无预期文件清单、总数、内容哈希或提交结束帧。首次审查阶段在本地对原始接收器复现：只传 1 文件或只发 run 标记均生成 `.done`；文件中途截断的对照用例才生成 `.fail`。因此“断连都检测到”的结论过强。本次正常查询的外层驱动额外强制 32 文件及摘要一致，防止把不完整结果算作有效样本；未改被测原始接收协议。

5. **输入和目录未隔离。** `recv_server.py` 直接拼接网络提供的标签和文件名，并删除同名 run 目录原有文件。本地无害临时目录实验确认 `../../escaped.txt` 可越出接收根目录。该端口无认证；重名 run 还与消费器永久 `done_runs` 集合冲突。

6. **消费器仍有边界缺陷。** 首文件未出现时 `t_start=None`，watchdog 条件永远不成立；空 `.done` 会在异常捕获块外执行 `perf_counter()-None`；零匹配批次 `SUM` 为 NULL 时 `int(None)` 失败。空 `.done` 导致进程退出已在本次真实端到端链路复现；首文件 watchdog、零匹配批次仍是静态发现，不声称已完成故障注入。数据通路也将多个 row group 的列数据覆盖到最后一个组，不能泛化到任意 Parquet；当前复用数据已确认每文件只有一个 row group。

7. **复现依赖没有完整入库。** producer 导入的 `runs/mask-phase1/mask_phase1_remote.py` 不在分支中；最终 resident 性能驱动也未发现完整可独立运行的仓库入口。干净重建后首次 FGAC 请求失败，定位到计划编译器缺少 `lake.sales.store_sales` 白名单。与旧部署逐行比较，只有这一行差异；本次显式记录补丁并重启，保留失败证据，没有悄悄复用旧进程。

8. **特殊格式与泄露约束。** 固定五列、宽度/字节序、PLAIN DATA_PAGE_V1、ZSTD、NULL=-2 与掩码=-1、源 footer/统计量复用均是方案约束。当前数据不存在真实 -2 值冲突，不代表其他数据也没有。统计量泄露已被原报告接受，不能把这一较弱泄露模型与更严格方案不加说明地视作同等保护。

9. **最新常驻管道不能沿用旧压缩传输字节结论。** `mask_e2e_server.py` 直接 `sendall(payload)`，payload 为解压后拼装的 Parquet，没有传输压缩；32 文件每次都发送。最新报告 §14.6 仍引用“VPN 口径 1.2MB 控制流”作为低选择率字节优势，不能代表当前真实 R→E TCP 数据流。原先 tar/zstd 传输的 1.2–239MB 与当前无压缩常驻管道是不同方案，时间和字节指标不可拼接。

10. **通用性和资源代价没有被当前规模证明。** `ProcessPoolExecutor.map` 按输入顺序产出结果，不是文档描述的完成顺序；提交全部文件也没有显式字节背压。父进程可持有已完成但尚未发送的 payload，内存不能简单按“一个文件约 25 MB”估算。全局串行 accept、硬编码五列与案例标签、空结果和多 row group 处理限制，均需要在声明通用 SQL/多租户服务前解决。将 FGAC 的 Arrow 转换开销直接称为不可避免的“逐单元安全处理”，也缺乏隔离实验：这同时比较了布局、格式与引擎实现。

11. **部分观测字段被过度解读。** 常驻消费器一次读取所有 pending 文件，输出的 `batches=len(processed)` 实际是文件数，并非 Spark 聚合批次数，不能据其为 32 就声称“逐文件执行 32 批”。`first_batch_lag` 在首次看到文件后立即设置起点，接近零也不等于请求到首批延迟。此次性能只用独立外层端到端时钟，不依赖这些字段推导耗时。

12. **最新对齐脚本实际上关闭了 NATIVE 的 Ranger。** 早期 `tpcds_benchmark.py` 为 NATIVE 选择 `native-conf`，但最新 `mask_aligned_bench.py:52` 为所有模式选择普通 `conf`。归档的旧部署与新副本均无 `spark.sql.extensions`，而 `native-conf` 明确包含 `RangerSparkExtension`。原配置真实端到端拒绝检查中，denied 用户仍返回 27,668 行、alice 未授权列仍返回 3 行。不能沿用早期启用 Ranger 的负向测试为最新计时背书；性能表中的 NATIVE 必须标为未启用 Ranger 的原始读取参考。

## 清理、重建与数据复用

- 使用绑定本机 WLAN 地址的 SSH socket，连接 R `:10023`、E `:10025`；查询数据通过服务器内网传输，不经过本地 VPN。
- 停止经 PID/命令/归属确认的 R 端 23 个、E 端 13 个旧 TPCDS/MASK 相关进程，确认没有目标存活；删除已盘点的旧 `/dev/shm/mask-pipe`。
- 旧脚本、配置、日志先归档到远端受限 `private` 目录；不删除其他项目或底层持久存储。
- 新建两端 `runs/review-mask-20260918/runtime`，从固定提交装载代码；重编译 E 端 ArrowSocketSource 并核验实际加载 JAR 的全部 class 字节码与新编译结果相同，重编译 R 端授权 sidecar，启动全新 JVM/服务，使用新临时目录和新投递目录；重新生成 skeleton。
- 对 S3 原表与 32 个待复用布局文件逐列逐行比较，允许的转换仅为已声明 NULL→-2。合计 28,800,991 行全部一致；每文件 1 row group；真实值 -2 冲突为 0。记录布局 SHA256、行数、NULL 数和 codec。
- 持久 MinIO/目录及策略存储保留。重新预热后的性能属于**干净进程的暖态**，不是清空整台共享服务器 OS 页缓存后的冷启动性能。

## 本次端到端协议

统一由 E 端单调时钟计量发起请求到最终输出；MASK 包含网络请求、R 生产、LAN 完整传输、E 消费和同样的双盐 xxhash64 聚合。三类路径均为常驻新会话；服务启动不计入暖态请求延迟。

最终资源对齐对照：八个选择率，每模式每案例完整预热一次，正式 3 rep，案例顺序固定随机种子打乱，三模式顺序以循环拉丁方平衡。NATIVE/FGAC/MASK2 同轮串行交错；FGAC 显式启用分支中单独提供的背压补丁。补充原报告 CPU 部署方式的低/中/全量端到端复现，以及 MASK1 串行端到端敏感性检查；补充组不混入主比较。由于 MASK 缺少授权且原对齐 NATIVE 未启用 Ranger，本组只能比较数据通路，不能称为完整访问控制系统的安全等价比较。

资源对齐组 E 上相关进程统一限定 2 个 CPU；R 的 FGAC 与 MASK2 限定相同 2 个 CPU。该组比原报告的 `local[2]` 更严格：Spark task 并行度不等于 JVM/辅助线程的总 CPU 配额。原配置复现组恢复未绑核方式，E/FGAC 保留 `local[2]`、MASK16 使用 16 进程，结果单独展示。

NATIVE 是直接读取参考，不额外运行 R 端查询算子；这里没有声称 NATIVE 与双节点方案的总计算预算相同。严格资源对齐的主要比较是 FGAC 与 MASK2。

首组直接使用主源码 `streaming/server.py`，未应用独立的 `patch_backpressure.py`；核对旧部署后发现此差异，主动停止并保留为 `diagnostic-only.json` 标记的诊断证据。该组不进入最终性能表。补丁只替换 `produce()` 的背压实现，保留当前分支其余逻辑，记录前后哈希后重启 FGAC 并重跑整个最终对照，不混合不同服务版本的测量。

每次 MASK 必须收齐 32 文件，并与本次新 NATIVE 参考的行数与两项哈希和逐项相等；不根据日志中的 `equal=true` 自证。正常结束后另做汇总完整性、唯一 rep、结果摘要与历史参考校验。

计时终点为 E 端完整消费五列并得到相同聚合摘要。摘要生成在计时内，驱动对摘要及文件数的外层断言决定样本是否有效。CPU 配额对齐不等于所有资源都已穷尽优化：JVM 堆保持原配置 2 GB，未给 Python 和整机内存设置同等 cgroup 上限；当前是大内存共享机器上的单客户端测试，不能外推内存受限、冷缓存、并发或尾延迟表现。每组只有少量重复，报告中位数和范围，不宣称细小差异具有统计显著性。

## 新端到端结果

**正常查询 144/144 次摘要一致，其中正式计时 108 次、预热 36 次。** 全部逐条与本次 NATIVE 参考及仓库历史 NATIVE 摘要独立比较，未依赖 `equal` 标志；复测后 32 个布局文件 SHA256 均未变化。

### A. FGAC 与 MASK2 等 CPU 配额通路对照（授权不等价）

FGAC 已启用文档所述背压优化；E 端 2 CPU，FGAC/MASK2 的 R 端各 2 CPU。每单元格为 3 次**真实端到端**测量的中位数，单位秒；百分比为中位数之比减一，负值表示 MASK 更快。

|---|---:|---:|---:|---:|---:|---:|
| 0.1% | 4.844 | 4.896 | 5.680 | +16.0% | +17.3% | 5.394–12.198 |
| 1% | 4.805 | 4.835 | 5.467 | +13.1% | +13.8% | 5.452–5.746 |
| 10% | 5.622 | 6.504 | 5.881 | -9.6% | +4.6% | 5.810–6.298 |
| 47.7% | 8.202 | 12.290 | 8.412 | -31.5% | +2.6% | 8.010–8.507 |
| 57.5% | 9.035 | 15.458 | 9.727 | -37.1% | +7.7% | 9.593–9.729 |
| 71.8% | 10.406 | 16.339 | 9.542 | -41.6% | -8.3% | 9.381–10.092 |
| 86.0% | 10.955 | 19.848 | 11.240 | -43.4% | +2.6% | 11.139–11.316 |
| 100% | 10.276 | 19.532 | 10.027 | -48.7% | -2.4% | 9.964–10.391 |

**解读：** 低选择率 0.1%/1% 下 MASK2 分别比 FGAC 慢约 16%/13%，比 NATIVE 慢约 17%/14%；中高选择率 47.7%–100% 下对 FGAC 的中位优势约 32%–49%。优势不是只靠 16 进程才出现，但“低选择率始终接近 NATIVE、差距不超过约 8%”不能跨资源条件推广。

低选择率出现一次 12.198 秒的 MASK2 请求；71.8% 的 FGAC 也有明显波动。所有有效样本均保留，没有依据速度删除离群值。3 次重复不支持“始终稳定”或尾延迟保证，完整最小/最大及逐 rep 配对比率见 summary.json。

### C. 实际传输量与端到端故障

正常 MASK 查询每次发送 **806,898,847 字节（806.9 MB）Parquet 净载荷**，另有很小的帧头/TCP 开销，8 个选择率均相同。这不是旧压缩路径的 1.2–239 MB；两种路径的数据不能组合成一个性能结论。

以下检查使用真实 R 生产器→LAN→接收器→Spark 全链路；在正常性能测量完成后执行：

| 检查 | 预期 | 实际结果 |
|---|---|---|
| 无效 token / denied 主体请求 MASK 全表 | 拒绝 | 返回与 NATIVE 全表一致的 28,800,991 行摘要 |
| R→E 在第一个完整文件后断连 | 请求失败，不提交结果 | 接收器写 .done，消费器输出部分数据的成功摘要 |
| R→E 只传 run 标记后断连 | 本请求失败，服务继续可用 | 接收器写空 .done，消费器 TypeError 退出 |
| 原对齐 conf 的 NATIVE denied 用户 / alice 未授权列 | 拒绝 | 两项均放行：分别返回 27,668 行及 3 行 |
| 改用 native-conf 启用 Ranger 后的上述两项 | 拒绝 | 两项均正确拒绝 |
| FGAC 无效 token / 未授权列 | 拒绝 | 两项均正确拒绝 |

因此：**特定数据通路正常结果正确，但 MASK 授权与故障隔离不合格，原对齐 NATIVE 还关闭了 Ranger，不能认可“安全等价的公平比较”及“全场景可靠”的总判断。** 表中 NATIVE 耗时仅代表原脚本的直接读取参考，不是启用 Ranger 后的授权基线耗时。外层复测驱动能用文件数与摘要检测部分结果，不等于服务自身已经具备拒绝部分提交的能力。

复测收尾已停止临时 MASK 工作池、确认 E 端测试工作进程退出并清理本次共享内存投递目录；保留重建的 FGAC/授权服务和已验证的持久数据。

## 建议修正顺序

1. 先把 MASK 接入可信授权契约：由服务端确定主体、允许的行/列与策略版本，再执行业务谓词；禁止客户端阈值替代授权。使用授权有效位或明确的行删除语义，不能依赖当前正数价格谓词恰好排除哨兵。
