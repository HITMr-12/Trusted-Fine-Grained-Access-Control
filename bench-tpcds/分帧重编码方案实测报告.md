# Parquet 分帧重编码方案实测报告

日期：2026-09-17　场景：bench_full_1_0（28,800,991 行，90% 权限，随机分布）　对照：FGAC Arrow IPC 路径（第一轮基线）

## 结论（先看这里）

分帧重编码方案**功能正确、安全语义不破、线上字节量下降 4.5×**，但**端到端延迟不降反升：25,736ms vs FGAC 14,239ms（1.81×）**。根因不是带宽，而是两点：

1. **传输与消费零重叠**——R 端必须等 Spark `write.parquet` 整个 job 提交后才发帧（首帧时刻 16.2s ≈ 编码完成时刻），而 Arrow 路径的传输与 E 端消化几乎完全重叠（total ≈ max(R 13.4s, E 14.1s)）。
2. **CPU 税换成 CPU 税**——省下的 1,179MB 传输税（≈4.5s @3.8ms/MB，原本嵌在流内且与消费重叠）被 R 端 Snappy 全量重编码 + E 端 Parquet 全量解码的 CPU 成本替代，净亏损。

与压缩 A/B 结论一脉相承：**本场景的瓶颈是端到端 CPU（编码/解码/搬运），不是链路带宽**。

## 实现架构（裁决原则：R 端一次编码、E 端一次解码）

- **R 端** `serve_remote_tpcds_frames.py`（端口 18836）：复用既有 ticket/鉴权合约；`do_get` 内由 Spark 自己完成"解码源表 → 行级授权过滤 → snappy Parquet 编码"（`prepared.frame.write.option('compression','snappy').option('maxRecordsPerFile',250000)`），每个输出 part 文件（≈2.6MB、250k 行）作为一个 binary Flight 帧发出。Python 只搬运字节，不做任何编解码。
- **E 端** `frame_bridge_tpcds.py`：bridge 纯字节中继——binary 帧原样写本地临时目录 `part-*.parquet`，流结束后 `spark.read.parquet(dir)`。**bridge 零解码**；唯一一次解码发生在 E 端 Spark 引擎原生 Parquet reader 内。
- 安全语义：过滤仍全部发生在 R 端 Spark 内（compiled frame 含行策略），线上只有被授权行的字节；digest 与 NATIVE 参考全等（见下）。

## 性能 A/B（同机交错，warmup 1 + 5 reps，中位数）

| 指标 | FGAC (Arrow IPC) | FGAC-FRAMES (Parquet 分帧) |
|---|---|---|
| **total_ms** | **14,239** | **25,736** |
| E 端 prepare_ms | 58（prefetch 重叠） | 16,887 |
| E 端 action_ms | 14,125 | 8,837 |
| E 端 e_cpu_ms | 29,025 | 21,583 |
| 线上字节 | 1,512.1 MB | **333.2 MB（4.54×↓）** |
| 批/帧数 | 3,536 批 × 8192 行 | 128 帧 × 250k 行 |
| R 端 wall | stream 13.4s（scan+IPC，边扫边传） | write 15.8s + 传 0.85s = elapsed 16.7s |
| R 端 cpu_ms | 59,000–79,000 | 33,500 |

### 成本结构解读

**FGAC 路径是重叠流水线**：R 端流式产出 13.4s ∥ E 端边收边算 14.1s → total = max ≈ 14.2s。1,512MB 的传输税（≈5.7s）嵌在流水线里被隐藏了大半。

**FRAMES 路径是两段串行**：R 端编码 15.8s（E 端干等，首帧 16.2s 才到）→ 传输 0.85s（333MB 带宽极充裕）→ E 端解码+digest 8.8s。total = 16.9 + 8.8 ≈ 25.7s。

注意 R 端 write 15.8s 与 stream 13.4s 的差仅 ~2.4s——**Snappy 编码本身不是主要矛盾**；主要矛盾是 Spark 写 Parquet 必须 job 完成才有完整文件（v1 接受了这个结构），重叠性归零。若 v2 做到帧边写边传 + E 端提前扫描，理论下限 ≈ max(16.7, 8.8+ε) ≈ 17s，仍慢于 Arrow 路径 14.2s——因为 333MB 的编码 CPU + E 端解码 CPU 合计高于 Arrow 路径被重叠隐藏的传输税。

## v1 已知局限（诚实清单）

1. 传输与 E 端扫描零重叠（job-commit 后发送；bridge 先落盘再 `read.parquet`）。
2. E 端多一次磁盘往返（318MB 写 + 读）。
3. `maxRecordsPerFile` 在过滤后生效，帧大小随选择率浮动。
4. 仅单 case（bench_full_1_0）验证；未跑小 case 与 inline 对照。

## 路线取舍建议

| 路线 | 预期 | 依据 |
|---|---|---|
| 分帧 v2（边写边传 + 内存 FS 提前扫描） | ~17s，仍不及 Arrow 路径 | 重叠修复只能追回串行损失，编码/解码 CPU 差追不回 |
| **原样回传未过滤源 Parquet + 页级短路** | 90% 全权场景字节→接近源体积 | 跳过 R 端重编码；但随机分布下短路天花板 0%（见页级短路实测），只对高聚簇/排序数据有效 |
| 聚合下推（partial agg 到 R 端授权过滤后执行） | Arrow 流 1,442MB → KB 级 | 对聚合语句是数量级收益，对 SELECT * 无效 |
| 接受 Arrow 路径，优化其税 | LZ4/ZSTD 已实测只回收 13% | 税在 CPU 搬运，压缩无解 |

**判断**：在"90% 权限 + 随机分布 + SELECT 列集"这一主攻场景下，Parquet 分帧重编码不应替代 Arrow 路径；它的价值在"全权 SELECT *"（R 端甚至不用过滤，可直接原样回传源文件分片，编码次数=0）和聚簇数据的页级短路。建议下一步要么回到原样回传路线，要么把分帧方案的范围收窄到全权场景。
