# 掩码管线远端 phase-1 报告（真实 store_sales · R/E 架构 · 高低选择率）

日期：2026-09-17 ｜ 数据：真实 TPC-DS store_sales，28,800,991 行 / 32 文件（S3/MinIO 源只读）
结论：**正确性全链路通过（R 内部 sha1 全等 + 跨机 E 端 Spark 聚合全等）；性能上掩码通路在高选择率（90%）显著优、低选择率（2%）劣于过滤通路——存在明确的切换阈值，混合架构是最优解。**

## 1. 验证结论（三重证据链）

| 层 | 验证 | 结果 |
|---|---|---|
| R 内部 | 每用例 digest(原表+策略filter) == digest(掩码投递+信道合成+策略filter)，逐列 SHA1 | ✓ 三用例全等 |
| 跨机 E 端 | E 机 Spark 引擎读投递文件 + 注入策略 filter，count/sum/min/max 与 R 参考聚合逐项相等 | ✓ low（536,919 行）、high（24,829,819 行）全等 |
| 物理不可变 | S3/MinIO 源经 EC 分片只经 S3 API 读取；布局文件写后再未修改；投递为独立副本 | ✓ |

语义说明：E 端以 `AND` 注入策略谓词（`ss_store_sk = 1` / `IN (46店)`），掩码行（哨兵 -1，域外值）被引擎过滤，用户可见结果与过滤方案完全等价；位图/索引信道合成的谓词列与文件内掩码列逐元素相等（等价性在 R 端已证）。

## 2. 选择率设置（真实数据）

- **high**：`ss_store_sk IN S90`（46 店，登记时域已知，k=46 索引 1B/行），24,829,819 行（**90.3%**）

## 3. 性能实测（R=10023 生产，E=10025 引擎）

| 用例 | R 掩码生产* | R 读投递 | E 引擎（Spark，含启动~4s） | 线上量 |
|---|---|---|---|---|
| low（1.95%） | **6.00s**（补 28.2M 行） | 1.39s | 9.3s | 580MB（位图 3.6MB） |
| high（90.3%） | **3.23s**（补 4.0M 行） | 1.22s | 16.4s | 608MB（+索引 28.8MB） |
| full（100%） | **2.59s**（纯拷贝地板） | 1.38s | — | 580MB |

\* R 掩码生产 = 读布局 807MB + 页游走 memset + 写投递 807MB（冷 I/O）。成本分解：**拷贝地板 2.6s（读+写 1.6GB @ ~620MB/s），边际掩码成本 ≈ 0.12µs/行**（纯内存带宽，可忽略）。

E 端说明：9.3s/16.4s 为朴素 spark-submit（含会话启动 ~4s、两次作业 count+agg）；纯引擎读取信号取 R 端向量化读投递的 **1.2-1.4s（≈600MB/s→5GB/s 页缓存）**。传输计时（580MB）：VPN 中转 74s（zstd）为隧道假象；实验室内网 R→E 千兆/万兆下为秒级（前期 1.5GB Arrow 传输尾差实测仅 0.3-0.5s）。

## 4. 高低选择率分析（核心发现）

1. **掩码成本与通过率正相关、与"被掩码行数"正相关**：98% 被拒的 low 用例要补 28.2M 行（虽然 memset 本身便宜，但满文件拷贝地板不可省），R 端 6.0s；90% 通过的 high 用例只补 4.0M 行，3.2s。**低选择率是掩码通路的最差工况**。
2. **对照已部署 FGAC 基线**：high（≈100% 工况）FGAC 实测 14.2s（R 生产 12.8s）→ 掩码通路 R 3.2s + 内网传输 + E ~2s ≈ **6-8s，约 2× 提速**；low（2%）FGAC 已贴近 NATIVE 地板（选择率基线：0.1% 时 0.99×，地板 ~3.9s，输出小、传输少）→ 掩码通路 8s+ **反而更慢**。
3. **结论：掩码通路不是全局替代，而是高选择率专用通路**。最优架构是按登记时的先验选择率分流：**低选择率走 Arrow 过滤通路（输出小），高选择率走掩码通路（零重编码 + 谓词列信道）**——这正是此前"Page 直通/Arrow 混合"思想在掩码范式下的落点，且分流决策在登记权限时即可做出（先验知识第三次发挥作用：布局、信道、分流）。

## 7. 补充：布局公平性 + 压缩掩码实测（2026-09-17）

### 7.1 布局公平性（无压缩 + 关统计对基线的影响）

实测对照（5 列投影，28.8M 行，R 机）：

| | zstd 原始布局 | 掩码布局（无压缩 PLAIN） |
|---|---|---|
| 体积 | 250MB | 806MB（3.2×） |
| 冷/热读 | 2.9s / 2.8s | 3.5s / 3.4s（仅 +20%） |

- **无压缩**：NVMe 顺序读（~1.5GB/s）不是瓶颈，zstd 解码才是——3.2× 字节只换 +20% 读时。代价主体是掩码路径自己的磁盘税与拷贝地板；对照已部署 FGAC（Arrow 本无压缩、1.5GB）线上仍 2.6× 占优。
- **关统计**：防泄露的被迫选择（页/列 min/max 泄露被拒行取值），不帮助掩码路径任何环节。按"统计泄露暂时忽略"的决策，**本期可将统计打开**（掩码只改值区，统计保持建仓原值；E 端 filter 兜底语义）。
- **裁决**：同布局最严口径下 FGAC R 生产最多 12.8→11s（大头 collect+Arrow 重编码与源布局无关），**2× 结构差不变**。

### 7.2 压缩掩码实测（随机分布下判负）

| 管线（R 机实测） | 耗时 |
|---|---|
| zstd 重打包（不解码掩码） | 7.9s |
| 压缩掩码全管线（解码→掩码→列式重建→zstd 重编码） | **13.3~14.2s** |
| 无压缩字节掩码（本期方案） | 3.2s |

根因：随机分布下每页都含被拒行 → 每页必须解码→重建→重编码，往返成本是主体，与 writer 无关（分帧判负的同一根因再印证）。**本期不上压缩**。

### 7.3 二期方向：压缩 + 统计 + L1 聚簇 = 页三级分流

统计升级为机制承重件：全授权页原压缩字节直通（零编解码）；全拒页整页同值压至近零字节（或 E 按页头合成）；混合页聚簇后稀少可容忍。线上量 ∝ 通过率，低选择率短板（2% 时线上 ~5MB 级）同步修掉。

### 7.4 修正：解压不重编码（sidecar footer 方案）实测——可行，+2.3s 换 3.2× 存储

压缩与编码正交：zstd 无损解压后的页即 PLAIN 字节，掩码逻辑与无压缩路径逐字节相同；footer 仅需按新页长做前缀和簿记（ms 级），sidecar 页表可将其降到零解析。存储约束为 zstd + PLAIN（禁字典，字典码非值）。

| 方案 | R 生产实测 | 存储 | 线上 | E 端 |
|---|---|---|---|---|
| 无压缩布局（本期采用） | **3.2s** | 807MB | 580MB | 157ms |
| zstd 存储 + 解压掩码不重生 | **5.5s**（并行解码可至 ~4s） | **287MB** | 580MB | 相同 |
| zstd 存储 + 解压掩码重编码（判负） | 13.5s | 287MB | 287MB | +zstd 解码 |

裁决：7.2 的判负针对"重编码"往返；"解压不重编码"成立，代价是 +2.3s R 墙钟换 3.2× 存储。**本期墙钟优先维持无压缩布局**；该方案列为存储受限备选，sidecar 页表列为二期页三级分流承重件。
